# System Requirements

## 1. Purpose

This document defines the functional, non-functional, and data requirements for the Minimum Viable Product (MVP) of the Academic Chat Assistant.

The requirements are derived from the project problem definition and MVP scope and are intended to guide implementation and evaluation.

The system will integrate Large Language Models (LLMs) and Retrieval-Augmented Generation (RAG) to provide educational programming assistance supported by verifiable technical documentation.

The requirements prioritize technical correctness, educational usefulness, source traceability, version compatibility, modularity, and maintainability.

## 2. Functional Requirements

### FR-01 User Query Input

The system shall allow a user to submit a programming-related question through the user interface.

The query may include:

- natural-language questions;
- source code;
- compiler error messages;
- runtime error messages;
- descriptions of incorrect program behavior.

### FR-02 Programming Language Support

The system shall support programming-related interactions for:

- C;
- C++;
- Python.

The system is not required to support additional programming languages in the MVP.

### FR-03 Code Input

The system shall allow source code to be included as part of a user request.

The submitted code shall be transmitted to the backend together with the associated user question.

### FR-04 Request Validation

The backend shall validate incoming requests before processing them.

At minimum, the system shall verify that:

- the request contains valid input;
- required fields are present;
- invalid or malformed requests are rejected using an appropriate API response.

### FR-05 LLM Interaction

The system shall send the user request and required context to the configured Large Language Model.

The context may include:

- the current user question;
- relevant conversational history;
- source code or error messages submitted by the user;
- technical documentation retrieved through RAG;
- associated source and version metadata when applicable.

The interaction with the language model shall be performed through a dedicated LLM integration layer.

### FR-06 Model Provider Abstraction

The system shall isolate application logic from the specific LLM provider or execution mechanism.

The application shall interact with the language model through a common interface so that the underlying provider can be replaced without modifying the main API, frontend, or RAG retrieval logic.

The architecture shall support:

- externally hosted LLMs accessed through APIs;
- locally executed LLMs.

The initial implementation will use GPT-OSS-120B through the Groq API.

Implementing multiple providers simultaneously is not required for the MVP.

### FR-07 Response Generation

The system shall return a generated response to the user after processing a valid request.

The response may contain:

- conceptual explanations;
- code explanations;
- error explanations;
- debugging guidance;
- suggested corrections;
- small code examples;
- explanations of expected program behavior;
- relevant technical references;
- compatibility information when supported by available documentation.

The system shall distinguish supported technical information from conclusions that cannot be verified using the available evidence.

### FR-08 Educational Response Orientation

The system shall prioritize explanatory guidance rather than providing only a final solution when the user requests help with programming problems.

Responses should, when applicable:

- identify the relevant problem;
- explain the probable cause;
- describe the reasoning required to understand it;
- suggest an appropriate correction or next step;
- provide small examples that support understanding;
- reference relevant technical documentation when necessary.

### FR-09 Conversation Context

The system shall preserve the conversational context required to support follow-up questions during an active interaction.

The context management mechanism shall allow relevant previous messages to be incorporated into subsequent requests.

The MVP is not required to maintain permanent long-term memory across unrelated sessions.

### FR-10 Frontend Response Display

The frontend shall display the response returned by the backend in a readable format.

The interface shall support the visualization of:

- normal text;
- programming code;
- technical explanations;
- source references;
- relevant compatibility information;
- uncertainty or insufficient-evidence messages.

### FR-11 Error Handling

The system shall handle errors generated by the application, RAG components, or LLM provider.

Potential errors include:

- invalid user input;
- unavailable LLM provider;
- model inference failures;
- document retrieval failures;
- unavailable knowledge base;
- invalid or missing configuration.

When a request cannot be completed, the user shall receive an understandable error response rather than an unhandled application failure.

### FR-12 Evaluation Task Execution

The project shall provide a mechanism to evaluate the assistant using a predefined set of programming-related tasks.

Evaluation tasks may include:

- conceptual questions;
- code explanation;
- compiler error interpretation;
- runtime error analysis;
- logical error identification;
- code correction;
- language-standard compatibility questions;
- compiler or interpreter version compatibility questions;
- questions requiring retrieval of technical documentation.

The evaluation process shall support comparison between responses generated with RAG and responses generated without retrieved documentation.

### FR-13 Evaluation Result Recording

The evaluation process shall allow results to be recorded for later analysis.

Recorded information may include:

- task identifier;
- programming language;
- input prompt;
- generated response;
- expected behavior or reference answer;
- retrieved document identifiers;
- source references;
- evaluation scores;
- model configuration;
- retrieval configuration;
- relevant language or compiler version.

### FR-14 Technical Documentation Ingestion

The system shall provide a mechanism to ingest selected technical documentation into the RAG knowledge base.

The ingestion process shall support documents relevant to:

- programming language syntax and semantics;
- standard library functionality;
- language standards;
- compiler documentation;
- interpreter documentation;
- version compatibility;
- common programming errors.

Documentation shall be obtained from a controlled collection of selected sources.

Automated web crawling and continuous synchronization with external websites are not required for the MVP.

### FR-15 Documentation Review

Documentation shall undergo an initial review before being incorporated into the knowledge base.

The review shall consider:

- source reliability;
- technical relevance;
- document integrity;
- applicable language or compiler versions;
- availability of source references;
- licensing or usage restrictions;
- conflicting or outdated information when identified.

Documents that do not meet the established acceptance criteria shall not be incorporated into the active knowledge base.

The MVP does not require a fully automated documentation verification system.

### FR-16 Document Processing and Indexing

The system shall process accepted technical documentation to prepare it for retrieval.

The processing workflow shall include:

- document loading;
- text preprocessing;
- document fragmentation;
- metadata association;
- embedding generation;
- indexing and storage.

The indexing process shall preserve the relationship between document fragments and their original sources.

The selected indexing and storage implementation shall remain independent from the LLM provider.

### FR-17 Technical Documentation Retrieval

The system shall retrieve relevant technical documentation from the knowledge base when factual grounding is required.

The retrieval process shall:

- accept a programming-related query;
- search the indexed knowledge base;
- identify relevant document fragments;
- return the retrieved content;
- preserve associated metadata and source references.

The retrieval component shall operate independently from the specific LLM provider.

The MVP does not require advanced multi-stage retrieval or complex reranking mechanisms.

### FR-18 Language and Version-Aware Retrieval

The system shall use available metadata to restrict or prioritize retrieved documentation according to the technical context of the user request.

Relevant constraints may include:

- programming language;
- language standard;
- compiler implementation;
- compiler version;
- interpreter implementation;
- interpreter version.

The system shall distinguish between:

- features defined by a programming language standard;
- features implemented by a specific compiler;
- features available in a particular interpreter version.

When the user specifies a language standard or compiler version, the system shall use that information during retrieval when corresponding metadata is available.

The system shall not assume that a compiler fully supports every feature of a language standard merely because it recognizes that standard.

If the required version information is missing or ambiguous, the system shall avoid presenting version-specific compatibility claims as verified.

The supported version ranges shall follow the approved project scope and the documented coverage of the knowledge base.

### FR-19 Retrieved Context Integration

The system shall incorporate relevant retrieved documentation into the context provided to the LLM.

The context construction process shall combine, when applicable:

- the user question;
- relevant conversational history;
- submitted source code or error messages;
- retrieved technical documentation;
- relevant language and version information;
- source references.

The system shall preserve a distinction between user input, retrieved documentation, and application instructions.

The implementation shall avoid including unnecessary retrieved information that does not contribute to answering the user's question.

### FR-20 Source Traceability

The system shall preserve the relationship between retrieved technical information and its original documentation source.

At minimum, retrieved documents shall include sufficient information to identify:

- the original document;
- its source or publisher;
- its reference or URL, when available;
- the relevant document fragment;
- applicable version information when relevant.

Generated responses shall provide traceable references when retrieved documentation is used to support technical claims.

The system shall not generate fabricated source references.

### FR-21 Insufficient Documentation Handling

The system shall identify situations where the retrieved documentation does not provide sufficient evidence to support a technical claim.

When relevant evidence is insufficient, the system shall:

- avoid presenting unsupported claims as verified facts;
- acknowledge the limitation;
- communicate relevant uncertainty;
- avoid asserting unverified compiler or interpreter compatibility.

The system may provide general educational guidance when appropriate, provided that it does not present unsupported information as verified technical evidence.

### FR-22 Conflicting Documentation Handling

The system shall handle situations where retrieved documents contain conflicting technical information.

When relevant contradictions are identified, the system shall:

- preserve the references associated with the conflicting information;
- consider available version and source metadata;
- avoid combining incompatible claims into a single unsupported conclusion;
- acknowledge unresolved contradictions when reliable resolution is not possible.

The MVP is not required to automatically resolve every contradiction between technical sources.

### FR-23 Retrieved Content Safety

The system shall treat retrieved documents as untrusted input rather than authoritative application instructions.

The system shall not execute instructions, commands, or code embedded in retrieved documentation as part of the RAG workflow.

Retrieved content shall not be allowed to override application-level instructions or expose confidential configuration information.

The backend shall maintain separation between:

- system instructions;
- user input;
- retrieved documentation;
- model-generated output.

### FR-24 RAG Evaluation

The project shall provide a mechanism to evaluate the quality of the RAG workflow.

Evaluation shall consider:

- retrieval relevance;
- retrieval coverage for predefined tasks;
- correctness of source references;
- consistency between generated answers and retrieved documentation;
- version compatibility when applicable;
- appropriate handling of insufficient or contradictory documentation.

The evaluation shall use predefined queries and reference information.

The system shall allow retrieval performance and answer quality to be analyzed separately.

## 3. Non-Functional Requirements

### NFR-01 Modularity

The application shall be organized into clearly separated components for:

- frontend interaction;
- backend API logic;
- RAG ingestion and indexing;
- document retrieval;
- context construction;
- LLM integration;
- evaluation.

Changes to one component should minimize unnecessary changes to unrelated components.

### NFR-02 Maintainability

The source code shall follow a consistent project structure and naming convention.

Reusable logic shall be separated from endpoint or interface-specific code when appropriate.

RAG, LLM integration, and application logic shall have clearly defined responsibilities.

### NFR-03 Extensibility

The architecture shall allow future integration of:

- additional LLM providers;
- locally executed models;
- additional technical documentation;
- alternative embedding models;
- alternative retrieval mechanisms;
- additional evaluation methods;

without requiring a complete redesign of the application.

### NFR-04 Reproducibility

The project shall document the dependencies and configuration required to reproduce the MVP environment.

Model, retrieval, indexing, and evaluation configurations used in experiments shall be identifiable.

The documentation collection and indexing configuration used for an evaluation shall be traceable.

### NFR-05 Local Model Compatibility

The LLM integration design shall not assume that inference must be performed using an external API.

The architecture shall remain compatible with locally executed language models.

Local inference is not required to be implemented simultaneously with the initial external API integration.

### NFR-06 Usability

The user interface shall allow a student to submit a query and read the generated response without requiring knowledge of the underlying model or retrieval infrastructure.

Technical references and uncertainty messages should be understandable to the intended academic users.

### NFR-07 Response Time

The system should return a response within a reasonable period for interactive academic use.

Response time may depend on:

- document retrieval;
- context construction;
- selected language model;
- external API latency;
- available hardware.

No strict production-level latency requirement is defined for the MVP.

Response time should be recorded during evaluation when practical.

### NFR-08 Reliability

A failure in the LLM provider or retrieval component shall not cause the backend application to terminate unexpectedly.

Retrieval, indexing, provider, and inference errors shall be handled at the application level.

The system shall provide an understandable response when a required component is unavailable.

### NFR-09 Traceability

The system shall maintain sufficient information during evaluation to identify:

- the input used;
- the model or provider used;
- the retrieved documents;
- the source references;
- the generated response;
- the associated evaluation result.

Traceability shall support the investigation of incorrect technical explanations and unsupported compatibility claims.

### NFR-10 Security

The application shall not expose confidential credentials such as API keys in source code or version control.

Sensitive configuration shall be provided through environment variables or equivalent configuration mechanisms.

The system shall:

- validate external input;
- treat retrieved documents as untrusted data;
- prevent retrieved content from overriding application instructions;
- avoid executing untrusted source code or document content;
- handle retrieved and generated content safely when presenting it to users;
- avoid exposing confidential information through model requests or application responses.

### NFR-11 Scope Compliance

The implementation shall prioritize requirements explicitly defined for the MVP.

Features outside the defined scope shall not be considered mandatory for MVP completion.

Advanced RAG capabilities shall not be introduced unless required to satisfy a defined requirement or a demonstrated evaluation need.

### NFR-12 RAG and LLM Independence

The RAG implementation shall remain independent from the specific LLM provider.

The retrieval component shall return information through a consistent internal representation that can be consumed by the context construction process.

Changing the LLM provider shall not require redesigning the document ingestion, indexing, or retrieval components.

The embedding model used for document retrieval shall be treated as a separate component from the generative LLM.

Replacing the embedding model may require regenerating embeddings and rebuilding the corresponding index.

### NFR-13 Documentation Integrity

The knowledge base shall preserve sufficient metadata to identify the origin and applicable technical context of indexed information.

Document processing shall not intentionally alter the technical meaning of source material.

The system shall avoid combining documentation from incompatible versions without considering relevant metadata.

### NFR-14 Source and Version Traceability

Retrieved fragments shall maintain a traceable relationship with their original documentation.

The system shall preserve version-related metadata when available and applicable.

Compatibility statements shall not be presented as verified unless supported by the available documentation.

The MVP is not required to provide exhaustive compatibility verification across every compiler, standard, operating system, and architecture combination.

### NFR-15 Retrieval Security

Retrieved documentation shall be treated as external content with no authority to modify the application's behavior.

The system shall not interpret retrieved instructions as application commands.

The retrieval pipeline shall not require unrestricted file-system access, autonomous code execution, or unrestricted interaction with external services.

These restrictions shall apply independently of the configured LLM provider.

### NFR-16 Evaluability

The system shall support reproducible evaluation of retrieval performance and generated response quality.

The evaluation process should distinguish between:

- retrieval failures;
- insufficient knowledge base coverage;
- incorrect interpretation of retrieved information;
- unsupported generated claims;
- version compatibility errors;
- educational explanation quality.

Evaluation metrics shall be defined consistently and applied to a controlled set of representative tasks.

## 4. Data Requirements

### DATA-01 User Query Data

The system shall process programming-related user input consisting of natural language, source code, or error information.

### DATA-02 Conversation Context

The system shall maintain the minimum conversational history required for follow-up interaction.

The MVP does not require permanent storage of complete user conversations.

### DATA-03 Evaluation Dataset

The project shall contain a predefined set of programming tasks used to evaluate system performance.

Each evaluation task should include, where applicable:

- task identifier;
- programming language;
- task category;
- user input;
- expected behavior;
- reference answer or evaluation criteria;
- relevant language standard;
- relevant compiler or interpreter version.

### DATA-04 Evaluation Results

The evaluation process shall produce structured results that can be analyzed or compared across experiments.

Results should support separate analysis of retrieval quality and generated answer quality.

### DATA-05 Configuration Data

Model and application configuration shall be separated from core application logic when appropriate.

Configuration may include:

- LLM provider selection;
- model identifier;
- inference parameters;
- system prompt or prompt configuration;
- embedding model;
- retrieval parameters;
- knowledge base location;
- environment-specific settings.

### DATA-06 Technical Documentation

The project shall maintain a curated collection of technical documentation relevant to C, C++, and Python.

The collection may include:

- language references;
- standard library references;
- compiler documentation;
- interpreter documentation;
- language-standard compatibility information;
- relevant technical explanations.

Documents shall be reviewed before incorporation into the active knowledge base.

The initial collection does not need to provide exhaustive coverage of all supported language features.

### DATA-07 Document Metadata

Indexed documentation shall preserve sufficient metadata for retrieval and traceability.

Metadata may include:

- document identifier;
- document title;
- source or publisher;
- source URL;
- programming language;
- applicable language standard;
- compiler or interpreter implementation;
- applicable version or version range;
- document fragment identifier;
- document review status.

Metadata fields shall be populated when relevant information is available.

Unavailable metadata shall not be replaced with unsupported assumptions.

### DATA-08 Indexed Knowledge Base

The system shall maintain an indexed representation of accepted technical documentation.

The index shall support:

- retrieval of relevant document fragments;
- association between fragments and embeddings;
- access to document metadata;
- identification of original sources;
- filtering using available metadata.

The specific storage technology shall be selected through the architecture decision process.

### DATA-09 RAG Evaluation Data

The project shall contain a controlled collection of questions for evaluating the RAG workflow.

Evaluation data should include, when applicable:

- query identifier;
- programming language;
- relevant version information;
- input question;
- relevant reference documents or fragments;
- expected technical information;
- evaluation criteria.

The dataset shall support evaluation of both documentation retrieval and generated responses.

## 5. RAG Evaluation Metrics

The MVP evaluation shall consider retrieval performance and response quality separately.

### 5.1 Retrieval Metrics

The following metrics may be used to evaluate document retrieval:

| Metric | Purpose |
|---|---|
| Recall@k | Measures the proportion of relevant reference documents retrieved among the top-k results. |
| Hit Rate@k | Measures whether at least one relevant document is retrieved within the top-k results. |
| Precision@k | Measures the proportion of retrieved top-k documents that are relevant to the query. |

These metrics require predefined queries with identified relevant reference documents.

The evaluation process shall select the metrics appropriate to the available evaluation dataset.

### 5.2 Response Quality Metrics

Generated responses shall be evaluated using criteria such as:

| Metric | Purpose |
|---|---|
| Technical Correctness | Determines whether the response is technically accurate. |
| Explanation Correctness | Evaluates whether the reasoning and explanations are valid. |
| Groundedness | Evaluates whether technical claims are supported by retrieved evidence. |
| Source Traceability | Evaluates whether provided references identify the supporting documentation. |
| Version Compatibility | Evaluates whether claims respect applicable language, compiler, or interpreter constraints. |
| Educational Usefulness | Evaluates whether the response supports student understanding. |
| Clarity | Evaluates whether the explanation is understandable to the intended users. |

### 5.3 Comparative Evaluation

The evaluation process should compare:

- LLM responses generated without retrieved documentation;
- LLM responses generated with RAG.

Both configurations should use equivalent programming tasks and evaluation criteria.

The comparison shall help determine whether RAG improves technical correctness, evidence grounding, and source traceability.

Metric definitions, scoring procedures, and acceptance thresholds shall be specified in the evaluation protocol.

The MVP does not require a complex automated evaluation framework.

## 6. MVP Acceptance Criteria

The MVP shall be considered functionally complete when:

1. A user can submit a programming-related question through the frontend.
2. The backend successfully receives and validates the request.
3. The system can process questions related to C, C++, and Python.
4. The system can ingest a selected collection of reviewed technical documentation.
5. The documentation processing workflow can generate and store a searchable index.
6. The RAG component can retrieve relevant documentation for predefined evaluation queries.
7. The retrieval process can use available language and version metadata when applicable.
8. The system can incorporate retrieved documentation into the LLM context.
9. At least one LLM provider or local model implementation is functional.
10. The initial GPT-OSS-120B integration through Groq can generate responses.
11. The generated response is returned and displayed through the frontend.
12. Responses using retrieved documentation can provide traceable source references.
13. The system can communicate insufficient evidence without presenting unsupported compatibility claims as verified.
14. The system can acknowledge unresolved documentation conflicts identified during retrieval or response construction.
15. Follow-up interactions can use relevant conversational context.
16. The application logic is not directly coupled to a specific LLM provider.
17. The RAG implementation is independent from the selected generative LLM.
18. Retrieved documentation is treated as untrusted data rather than application instructions.
19. Predefined programming evaluation tasks can be executed.
20. Retrieval quality can be evaluated using the selected metrics.
21. Generated responses can be evaluated for technical correctness, evidence grounding, source traceability, and educational usefulness.
22. Evaluation results can be recorded and analyzed.
23. The complete workflow operates end-to-end through the frontend, backend, RAG, and LLM integration components.

Successful implementation does not imply complete knowledge coverage, perfect compatibility verification, or elimination of hallucinations.

The acceptance of evaluation results shall depend on the criteria established in the evaluation protocol.
